# ShadowGuard AI — Technical Write-up

**Project Title:** ShadowGuard AI

**Problem:** AI agents can combine tool access with untrusted content returned by those tools. Prompt-injected or misleading output may influence later calls, and sensitive operations should not execute solely because a model proposed them.

**Solution:** ShadowGuard AI is a local FastAPI application that routes the chat agent's tool calls through a policy interceptor. It evaluates registered-tool state, caller capabilities, trust evidence, intent signals, session taint, and deterministic action rules. Permitted calls run through adapters; blocked calls return structured errors; eligible database actions are simulated and staged for an operator decision.

**Innovation:** The demonstrator combines trust scoring, deterministic policy checks, session-scoped taint/provenance, in-memory SQLite shadow simulation, and human approval in one tool-call path. At approval time, staged action integrity, expiry, session/user context, current policy, taint sources, and the database snapshot are revalidated. A shared `APPROVAL_OPERATOR_TOKEN` bearer credential (minimum 32 UTF-8 bytes) protects approval and rejection decisions. This credential is not a user identity system, and other API routes remain unauthenticated.

**Technology Stack:** Python, FastAPI, Pydantic AI, FastMCP tool declarations, SQLite, SQLParse, scikit-learn, joblib, and HTTPX power the backend. The dashboard uses React/JavaScript, Vite, Tailwind CSS, and Lucide icons. GitHub Contents and Open-Meteo are the live integration APIs. FastMCP decorators are present, but this application does not start a standalone MCP transport; the chat path uses guarded Pydantic AI tools.

**System Workflow:** A user request enters FastAPI and is handled by the agent. The interceptor evaluates the selected tool call against capabilities, trust, intent, taint, and deterministic policy. GitHub/weather results are treated as untrusted and can taint the session. Eligible SQL is evaluated on an in-memory SQLite copy. Protected operations wait for an operator's bearer-token-authenticated decision; before execution, policy and snapshot state are checked again. Audit records and in-memory events feed the dashboard.

**Machine Learning:** The saved synthetic demonstration bundle contains a Random Forest trust classifier and a TF-IDF/Logistic Regression intent classifier. Training examples are generated by `backend/scripts/train_ml_models.py`; no labeled operational dataset is included. Model scores are advisory security signals, never authorization. The reported held-out synthetic metrics are wiring/reproducibility evidence only and do not demonstrate real-world detection performance. See [`ml-security-models.md`](ml-security-models.md).

**Security Impact:** The implemented checks can reject unsupported/prohibited SQL, calls outside declared capabilities, disabled or unknown tools, and selected high-trust access from tainted sessions. Shadow simulation and approval reduce the chance that a protected database mutation executes without review. Limitations include a shared token without named identity, unauthenticated non-decision API routes, session-level rather than server-graph taint, a local SQLite demo database, synthetic model data, and no automatic recovery for interrupted approvals. This is a prototype, not a production security guarantee.

**Validation:** The repository includes pytest coverage for policy, approval lifecycle, taint, model behavior, response safety, and mocked GitHub/Open-Meteo HTTP calls. Mocked tests do not verify live providers. Run `.\.venv\Scripts\python.exe -m pytest .\backend\tests` from the repository root and `npm run build` from `frontend`. Local benchmark methodology and observations are recorded in [`edge-first-architecture.md`](edge-first-architecture.md); they are not controlled production benchmarks.
